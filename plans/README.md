## Mandatory Review Loop

Each plan must pass this loop before it can move to DONE:

1. Implement the plan and run the plan's focused verification commands.
2. Run the full local gate required by the plan.
3. Request three independent read-only reviews of the resulting diff:
   - `reviewer` with `code-reviewer`: correctness, data loss, security,
     regression risk, and missing tests.
   - `architect` with `improve-codebase-architecture`: module/interface depth,
     seam placement, locality, leverage, and fit with `CONTEXT.md`.
   - `ponytail-review`: over-engineering only. It should list what to delete or
     shrink; it must not suggest removing safety checks, validation, audit, or
     tests required by the plan.
4. Fix every Critical/Warning/blocking finding from the three reviews, or record
   a one-line rejection with evidence in the plan's review notes.
5. Run the same three reviews a second time on the revised diff.
6. Fix every second-round blocker. If the second round finds a new blocker,
   repeat steps 4-6 until the three reviewers report no blockers, or stop and
   report why the remaining item should be accepted.

The second review round is required even when the first fix seems obvious. The
goal is to catch regressions introduced while fixing review feedback.

## Global Definition Of Done

A plan is DONE only when all items below are true:

- The plan-specific Done Criteria are checked off.
- Focused tests from the plan pass.
- `CI=true corepack pnpm test` exits 0.
- `CI=true corepack pnpm typecheck` exits 0.
- `CI=true corepack pnpm lint` exits 0.
- `CI=true corepack pnpm build` exits 0 when the plan touches runtime app code.
- `git diff --check` exits 0.
- The mandatory review loop has completed two rounds.
- Remaining review comments, if any, are explicitly rejected with file/line
  evidence and a short reason.
- The final diff touches only files allowed by the plan scope, except for
  `plans/README.md` status updates and directly necessary tests.
- No user-facing matching output introduces labels such as "top" or "priority"
  for suggested active participants; visible ordering stays plain `1`, `2`,
  `3`.

## Quality Criteria

Use these criteria in every review and final handoff:

- **Correctness**: reruns are idempotent, no operator artifacts are deleted, and
  failed writes cannot leave a successful audit trail.
- **Methodology**: matching selects an event composition with guest coverage,
  not a flat average ranking of active participants.
- **Data boundaries**: retention, payment phase, tenure, and payment history are
  active-eligibility evidence, not direct business-fit score inputs.
- **Traceability**: every selected or excluded active participant has stored
  evidence, risks, settings, and semantic status.
- **Minimality**: no new dependency, abstraction, setting, or table is added
  unless the plan names the need and no existing module can cover it.
- **Architecture**: matching scoring, semantic adapters, run orchestration, and
  UI rendering stay behind separate module interfaces.
- **Tests**: every non-trivial branch, parser, date window, transaction, and
  rerun behavior has a focused test.
- **Operations**: dry-run output is enough to inspect recent guest events before
  deploy, and degraded matching is visible without parsing raw JSON.

## Findings Considered And Rejected

- Use retention, payment phase, tenure year, and similar club facts as direct
  business-match score inputs: rejected for this methodology. Those facts are
  evidence for whether someone is an active participant, not for whether their
  business profile fits a potential participant.
- Replace LLM with code-only matching: rejected. Code should apply hard gates
  and measurable constraints; LLM should evaluate semantic fit on the remaining
  evidence-backed pairs under audit and movement limits.
- Deploy the current branch after green tests only: rejected. Current tests pass
  mechanics, but do not prove event composition quality, rerun safety, or
  operator-artifact preservation.
- Keep cross-format recent PAU visits as a soft default penalty only: rejected
  for this product iteration. The product rule is that people who visited any
  internal PAU format in the configured month/window must not be invited again.
